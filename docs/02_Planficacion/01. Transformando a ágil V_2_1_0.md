# 1. Estrategia de transformación ágil

## 1.1. Enfoque de ejecución

El proyecto adopta un enfoque híbrido:

**Componente planificado:**
- Objetivos y alcance aprobados.
- Cronograma e hitos.
- Presupuesto.
- Arquitectura general.
- Requisitos críticos de calidad.
- Control de cambios.

**Componente adaptativo:**
- Organización del Product Backlog.
- Desarrollo por iteraciones.
- Priorización por valor y riesgo.
- Pruebas y demostraciones incrementales.
- Refinamiento de historias de usuario.
- Corrección continua de defectos.

Se recomienda utilizar iteraciones de dos semanas dentro de la duración aprobada.

La asignación definitiva de historias a los sprints dependerá de la capacidad del equipo y de las dependencias técnicas.

## 1.2. Estructura del trabajo

La jerarquía propuesta es:

```text
Épica
 └── Historia de Usuario / Enabler
      ├── Subtarea frontend
      ├── Subtarea backend
      ├── Subtarea base de datos
      ├── Subtarea integración
      └── Subtarea pruebas
```

No todas las historias necesitan cinco subtareas.

Las subtareas deberán responder al esfuerzo real requerido.

## 1.3. Convención de identificadores

| Prefijo | Significado | Ejemplo |
|---|---|---|
| EP | Épica | EP-01 |
| US | Historia de usuario | US-001 |
| EN | Enabler técnico | EN-001 |
| RF | Requisito funcional | RF-003 |
| RNF | Requisito no funcional | RNF-001 |
| RN | Regla de negocio | RN-004 |
| CA | Criterio de aceptación | CA-01 |

Se mantienen los identificadores US-001 a US-024 y EN-001 a EN-007 para conservar la trazabilidad con el documento anterior.

## 1.4. Criterios de priorización

Se propone la siguiente clasificación para el refinamiento inicial del backlog:

| Prioridad | Definición |
|---|---|
| P0 — Crítica | Necesaria para construir o validar el flujo central del PMV |
| P1 — Alta | Aporta valor importante o satisface requisitos relevantes |
| P2 — Media | Funcionalidad complementaria o mejora progresiva |
| P3 — Condicionada | Requiere decisión de alcance, información o metodología adicional |

Estas prioridades son propuestas del asesor y deberán ser aprobadas por el responsable del Product Backlog.

No sustituyen las prioridades oficiales de la consigna cuando existan.

# 2. Definition of Ready (DoR)

Una historia podrá incorporarse a un sprint cuando:

1. Tenga identificador y título.
2. Esté relacionada con una épica.
3. Identifique el actor o beneficiario.
4. Describa la necesidad y el valor esperado.
5. Tenga criterios de aceptación verificables.
6. Identifique los requisitos asociados.
7. Tenga dependencias y bloqueos conocidos.
8. Disponga de información suficiente para su desarrollo.
9. Pueda dividirse o estimarse dentro de la capacidad del sprint.
10. Haya sido revisada por el responsable de priorización y el equipo técnico.

Si existen decisiones pendientes que impiden su implementación, la historia no debe declararse Ready.

---

# 3. Definition of Done (DoD)

Una historia o enabler será considerada terminada únicamente cuando cumpla los criterios aplicables.

## 3.1. Criterios generales obligatorios

1. La funcionalidad está implementada según su alcance aprobado.
2. Se cumplen todos sus criterios de aceptación.
3. Las validaciones necesarias están implementadas.
4. El código ha pasado revisión mediante Pull Request.
5. No existen defectos críticos o bloqueantes abiertos asociados al cambio.
6. Las pruebas aplicables fueron ejecutadas y documentadas.
7. El código se encuentra integrado en la rama correspondiente.
8. La documentación funcional o técnica afectada está actualizada.
9. Se conserva la trazabilidad con el requisito de origen.
10. La funcionalidad ha sido demostrada o verificada en un entorno controlado.

## 3.2. Condiciones técnicas según el tipo de historia

**Backend:**
- Validación de solicitudes.
- Manejo de excepciones.
- Respuestas HTTP apropiadas.
- Pruebas unitarias y de integración.
- Autorización cuando corresponda.

**Frontend:**
- Formularios funcionales.
- Estados de carga, éxito y error.
- Diseño responsive.
- Accesibilidad aplicable.
- Integración con API real o entorno controlado.

**Base de datos:**
- Migraciones versionadas.
- Integridad referencial.
- Validación de restricciones.
- Pruebas de persistencia.

**Optimización:**
- Validación de entradas.
- Detección de soluciones no factibles.
- Registro de parámetros.
- Resultados reproducibles cuando el algoritmo lo permita.
- Medición de rendimiento.

**Seguridad:**
- Secretos fuera del repositorio.
- Accesos no autorizados denegados.
- Protección de datos personales.
- Evaluación de vulnerabilidades aplicables.

## 3.3. Objetivos adicionales de calidad

Se propone utilizar herramientas de análisis estático y cobertura de pruebas.

El objetivo de cobertura del 80 % y el uso específico de SonarQube o CodeQL deberán confirmarse según la infraestructura disponible.

La cobertura porcentual no sustituye la aprobación de los casos de prueba críticos.

El despliegue en staging será obligatorio para una historia solamente cuando el flujo de integración y despliegue haya sido habilitado formalmente.

# 9. Consideraciones técnicas para el desarrollo

## 9.1. Frontend

**Tecnología:** React.

Responsabilidades:

- Formularios de pedidos y vehículos.
- Validación de entradas.
- Consumo de API.
- Visualización cartográfica.
- Dashboard.
- Comparación de escenarios.
- Gestión de estados de carga y error.

El frontend no deberá contener las reglas centrales del optimizador ni credenciales privadas.

## 9.2. Backend

**Tecnología:** Python y FastAPI.

Responsabilidades:

- API REST.
- Validación de solicitudes.
- Autenticación y autorización.
- Reglas de negocio.
- Orquestación del optimizador.
- Cálculo de métricas.
- Persistencia.
- Integración con proveedores externos.

Se recomienda separar controladores, servicios, dominio y repositorios.

## 9.3. Base de datos

**Tecnología:** PostgreSQL/PostGIS.

El modelo deberá considerar:

- Usuarios.
- Vehículos.
- Conductores.
- Clientes.
- Pedidos.
- Escenarios de planificación.
- Rutas.
- Paradas.
- Asignaciones.
- Resultados de optimización.

Las nuevas entidades deberán incorporarse al documento de base de datos antes de considerarse aprobadas.

## 9.4. Motor de optimización

El motor deberá:

1. Recibir entradas estructuradas.
2. Validar restricciones.
3. Construir el problema de optimización.
4. Ejecutar el algoritmo seleccionado.
5. Detectar soluciones no factibles.
6. Devolver asignaciones y secuencias.
7. Calcular indicadores.
8. Registrar parámetros y duración.
9. Entregar resultados mediante un contrato definido.

La selección entre OR-Tools, un algoritmo genético u otra técnica deberá justificarse mediante prototipos y pruebas.

## 9.5. Servicios geoespaciales

Los servicios externos deberán integrarse mediante adaptadores.

Se deben controlar:

- Errores de conexión.
- Cuotas.
- Tiempo de espera.
- Restricciones de licencia.
- Disponibilidad de datos.
- Calidad de coordenadas.
- Diferencia entre distancia geométrica y distancia vial.

No debe interpretarse el uso de OpenStreetMap como garantía automática de disponibilidad gratuita de cualquier servicio de ruteo, geocodificación o tráfico.

Los cambios que afecten la línea base del proyecto deberán contar con evaluación y aprobación.

Los cambios menores dentro del alcance podrán incorporarse mediante refinamiento del Product Backlog.

Cada modificación relevante deberá actualizar los documentos y requisitos asociados.
