# 04. Punto de control 1 - Cliente API

## Configuración central de servicios API

**Rama:** `feature/integracion-sprint-3`  
**Estado:** cambios locales, sin commit ni push  
**Alcance de este ciclo:** infraestructura HTTP y contrato público de salud. No se migraron todavía los CRUD desde Supabase hacia FastAPI.

## 1. Requisito identificado

Centralizar las solicitudes HTTP del Frontend, usar una URL de Backend configurable, preparar el envío de tokens Bearer, validar respuestas y transformar fallos técnicos en errores utilizables por la interfaz.

## 2. Contrato comprobado

Se utilizó el contrato verificado en Fase 3:

- Base configurada mediante `VITE_API_BASE_URL`.
- Operaciones protegidas con `Authorization: Bearer <token>`.
- Error Backend: `{error:{code,message,details}}`.
- Salud pública: `GET /health` con `status`, `application` y estado PostgreSQL/PostGIS.

## 3. Implementación

| Archivo | Función |
|---|---|
| `Frontend/.env.example` | Documenta URL del Backend y variables públicas Supabase sin incluir secretos reales. |
| `Frontend/src/config/env.ts` | Exige y valida una URL HTTP/HTTPS; elimina `/` final. |
| `Frontend/src/services/http.ts` | Cliente único para GET/POST/PUT/DELETE, token configurable, timeout, JSON, errores y decoder obligatorio. |
| `Frontend/src/services/backendHealth.ts` | Primer contrato runtime: valida la respuesta de `/health`. |
| `Frontend/src/vite-env.d.ts` | Tipos de las variables Vite. |
| `Frontend/src/services/http.test.ts` | Pruebas del URL base, token, sesión ausente, error Backend y contrato de salud. |
| `Frontend/package.json` y `package-lock.json` | Script `npm test` y Vitest 2.1.9. |

El cliente rechaza rutas absolutas: cada servicio debe proporcionar paths relativos. Esto impide repetir o desviar accidentalmente la URL del Backend en componentes.

La integración del token quedó preparada mediante `configureApiAccessToken`. Su conexión con la sesión Supabase corresponde al siguiente ciclo de autenticación; no se simuló una sesión.

## 9. Decisión del punto de control

La funcionalidad 1, **configuración central de servicios API**, queda técnicamente aprobada para continuar. La pantalla todavía usa los servicios Supabase originales porque el ciclo se detiene aquí antes de autenticación, conforme al punto de control solicitado.

Siguiente ciclo recomendado:

1. conectar `configureApiAccessToken` con la sesión real de Supabase;
2. verificar token válido, expirado y ausente;
3. comprobar acceso de `admin`, `operator` y `driver` contra FastAPI;
4. inspeccionar visualmente estados de autenticación y errores;
5. presentar el segundo punto de control antes de migrar los CRUD.
