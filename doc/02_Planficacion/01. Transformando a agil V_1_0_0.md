# 01. Transformando a ágil V_1_0_0

## 1. Definition of Done (DoD) Global del Proyecto

Para asegurar la calidad técnica y el cumplimiento de los Requisitos No Funcionales transversales (como accesibilidad, rendimiento y seguridad), ninguna Historia de Usuario (US) o Enabler será considerada como finalizada ("Done") a menos que cumpla de forma estricta y no ambigua con los siguientes criterios de calidad:

1. **Cobertura de Pruebas:** Cobertura de pruebas unitarias y de integración ≥ 80% verificada en el pipeline de CI/CD.
2. **Seguridad y Calidad de Código:** Análisis estático de código ejecutado (vía SonarQube / CodeQL) reportando **0 vulnerabilidades críticas o mayores**, garantizando la mitigación del OWASP Top 10 y el cumplimiento de la Ley N.° 29733 (Protección de Datos Personales).
3. **Revisión de Código:** Revisión de código (*Peer Review*) aprobada formalmente por al menos un par técnico senior mediante *Pull Request* en el repositorio oficial.
4. **Despliegue Continuo:** Despliegue automatizado ejecutable de forma exitosa en el ambiente de Staging / Pruebas, sin requerir intervención manual.
5. **Documentación:** Documentación de API y código completamente actualizada y accesible mediante OpenAPI/Swagger.
6. **Accesibilidad y Usabilidad (Frontend):** Las interfaces desarrolladas deben pasar el validador automático de accesibilidad WCAG 2.1 nivel AA.

## 2. Mapa de Épicas (Mapeo Jerárquico de RF)

Los Requisitos Funcionales (RF) han sido agrupados temáticamente en Épicas de desarrollo para gestionar las entregas incrementales del PMV.

- **EP-01: Gestión Core de Operaciones Logísticas:** Abarca la gestión y persistencia de vehículos, conductores, clientes y pedidos (Mapeo: RF-01, RF-02, RF-08, RF-09).
- **EP-02: Motor de Optimización y Despacho (Green VRPTW):** Contiene la lógica del algoritmo de ruteo y la re-optimización dinámica (Mapeo: RF-03, RF-07).
- **EP-03: Visualización, Monitoreo y Sostenibilidad:** Agrupa la cartografía, el dashboard de indicadores y los reportes de huella de carbono (Mapeo: RF-04, RF-05, RF-06, RF-10).

### 3.1. Historias de Usuario (Funcionalidades de Negocio)

#### US-001 — Registro e inventario de flota vehicular con parámetros ambientales

- **ID:** `US-001`
- **Título:** Registro e inventario de flota vehicular con parámetros ambientales
- **Épica Relacionada:** EP-01 Gestión Core de Operaciones Logísticas

**Redacción:**

> **Como** Administrador Logístico,  
> **quiero** registrar los vehículos de la flota especificando su capacidad de carga, consumo de combustible y factor de emisión de $CO_2$,  
> **para** disponer de los parámetros técnicos necesarios que permitan planificar rutas sostenibles y calcular el impacto ambiental de las entregas.

**Criterios de Aceptación (BDD):**

- **Escenario:** Registro exitoso de una unidad tipo furgón diésel.
  - **Dado** que el Administrador Logístico tiene los permisos adecuados y se encuentra en el módulo de "Flota"
  - **Cuando** ingresa una placa válida, tipo "Furgón", capacidad "1500 kg", consumo "30 km/L" y factor de emisión "0.15 kg/km"
  - **Entonces** el sistema debe almacenar el vehículo en la base de datos con estado "Operativo" y mostrar un mensaje de confirmación de registro exitoso.

- **Escenario:** Intento de registro con datos ambientales omitidos.
  - **Dado** que el Administrador Logístico está registrando una nueva unidad
  - **Cuando** intenta guardar el registro omitiendo el "factor de emisión de $CO_2$"
  - **Entonces** el sistema debe bloquear el registro, resaltar el campo faltante y mostrar una advertencia indicando que los parámetros ambientales son obligatorios para el optimizador.

#### US-002 — Generación de rutas optimizadas multicriterio

- **ID:** `US-002`
- **Título:** Generación de rutas optimizadas multicriterio
- **Épica Relacionada:** EP-02 Motor de Optimización y Despacho

**Redacción:**

> **Como** Gestor de Rutas,  
> **quiero** ejecutar el motor de optimización para los pedidos diarios y vehículos disponibles,  
> **para** obtener una asignación de rutas que minimice la distancia, el tiempo, el consumo de combustible y garantice el cumplimiento de las ventanas horarias.

**Criterios de Aceptación (BDD):**

- **Escenario:** Generación exitosa de ruteo bajo carga máxima permitida para el PMV.
  - **Dado** un conjunto operativo configurado con 150 pedidos válidos y 15 vehículos activos
  - **Cuando** el Gestor de Rutas acciona el botón "Generar Planificación"
  - **Entonces** el sistema debe procesar la matriz mediante la metaheurística y devolver una solución de rutas válida en un tiempo máximo de 45 segundos.

- **Escenario:** Prevención de generación de rutas por falta de datos.
  - **Dado** que existen 50 pedidos pendientes pero ningún vehículo marcado como "Disponible"
  - **Cuando** el Gestor de Rutas intenta iniciar la optimización
  - **Entonces** el sistema debe abortar el proceso inmediatamente y notificar que es imposible generar la ruta por falta de capacidad vehicular disponible.

#### US-003 — Interfaz de navegación simplificada en Modo Conductor

- **ID:** `US-003`
- **Título:** Interfaz de navegación simplificada en Modo Conductor
- **Épica Relacionada:** EP-03 Visualización, Monitoreo y Sostenibilidad

**Redacción:**

> **Como** Conductor de la flota,  
> **quiero** visualizar mi itinerario mediante un "Modo Conductor" simplificado y de alto contraste,  
> **para** poder seguir mi ruta y registrar entregas de manera intuitiva y segura sin distracciones mientras opero en campo.

**Criterios de Aceptación (BDD):**

- **Escenario:** Acceso a la vista simplificada de operaciones.
  - **Dado** que un Conductor inicia sesión en la plataforma web desde un dispositivo móvil
  - **Cuando** el sistema carga la pantalla principal
  - **Entonces** la interfaz debe adaptar su diseño mostrando exclusivamente: la ruta asignada, la lista de entregas pendientes con tipografía grande y alertas de tráfico.

- **Escenario:** Tolerancia a conectividad limitada (Sincronización local).
  - **Dado** que el Conductor se encuentra en una zona de San Juan de Lurigancho con baja conectividad móvil (2G/3G)
  - **Cuando** marca un pedido como "Entregado"
  - **Entonces** el sistema debe registrar la acción localmente de forma inmediata y sincronizar la actualización con el backend cuando la red alcance estabilidad.

### 3.2. Historias Técnicas (Enablers - Transformación de RNF)

#### EN-001 — Infraestructura asíncrona para motor de optimización (Rendimiento)

- **ID:** `EN-001`
- **Título:** Infraestructura asíncrona para motor de optimización (Rendimiento)
- **Épica Relacionada:** EP-02 Motor de Optimización y Despacho

**Redacción:**

> **Como** Arquitecto de Software,  
> **quiero** configurar un entorno de procesamiento backend asíncrono utilizando Python (FastAPI) y extensiones geoespaciales (PostGIS),  
> **para** soportar la concurrencia matemática de las metaheurísticas y garantizar tiempos de respuesta inferiores a 30 segundos en casos de re-optimización dinámica.

**Criterios de Aceptación (BDD):**

- **Escenario:** Pruebas de estrés de re-optimización dinámica.
  - **Dado** que la API de backend se encuentra procesando 3 re-optimizaciones simultáneas para diferentes sucursales
  - **Cuando** se inyectan nuevas interrupciones de tráfico
  - **Entonces** el servidor debe resolver y actualizar los JSON de respuesta de manera asíncrona sin superar el umbral estricto de 30 segundos de bloqueo de I/O.

- **Escenario:** Consultas de aislamiento de infraestructura (Green Software).
  - **Dado** que el algoritmo extrae la matriz de distancias
  - **Cuando** consulta PostgreSQL
  - **Entonces** la operación debe ejecutarse utilizando índices espaciales GIST (PostGIS) asegurando un consumo eficiente de CPU alineado con los estándares de Green Software.
