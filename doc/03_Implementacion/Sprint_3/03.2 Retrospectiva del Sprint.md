# 04.2 Retrospectiva del Sprint

## 1. Propósito y regla de validación

Este documento prepara la Retrospectiva del Sprint 3 usando evidencia técnica. No sustituye la reunión del equipo.

- Los hechos técnicos se presentan como observaciones verificadas.
- Las causas se presentan como hipótesis razonables, no como conclusiones personales.
- Las opiniones sobre coordinación, desempeño o decisiones del equipo quedan **pendientes de validación en la retrospectiva**.
- Las acciones propuestas no se consideran compromisos hasta que el equipo asigne rol responsable, prioridad y criterio de cierre.
- No se asignan responsabilidades a personas ni se inventan fechas.

## 2. Aspectos positivos observados

| Aspecto | Evidencia | Validación requerida |
|---|---|---|

| El diagnóstico distinguió interfaces de integraciones reales. | Se identificaron Supabase directo, FastAPI separado, simulaciones y contratos faltantes. | No requiere opinión; revisar si faltó algún módulo. |

## 3. Problemas identificados

### 3.1 Arquitectura e integración

- React mantiene acceso directo a Supabase, mientras FastAPI dispone de controles y contratos distintos.
- El cliente HTTP central fue preparado, pero los CRUD principales no fueron migrados.
- Autenticación Supabase y autorización FastAPI no se probaron extremo a extremo con tokens reales.
- PostgreSQL funcionó en pruebas aisladas, pero PostGIS no estuvo disponible.
- La solución usa SVG propio en lugar de Leaflet/OpenStreetMap previsto.

### 3.2 Funcionalidad del Sprint

- La generación actual es demostrativa y no resuelve un problema de optimización.
- Las rutas generadas no demuestran persistencia transaccional completa.
- Congestión, indicadores y ahorros se calculan o presentan localmente sin contratos y fuentes aprobados.
- La comparación de escenarios no dispone de entidad/endpoint/flujo verificable.
- Reoptimización carece de implementación y tiene alcance documental ambiguo.

### 3.3 Calidad y pruebas

- La cobertura total SonarQube es 9.6%; cobertura del código nuevo, 16.7% frente a 80% requerido.
- La mayor parte del Frontend carece de pruebas unitarias.
- Solo dos flujos E2E públicos pudieron aprobarse; seis se omitieron por dependencias funcionales reales.
- Persisten 56 errores y 2 advertencias ESLint registradas.
- No existe una base de prueba integrada con PostGIS, perfiles y tokens por rol lista para CI.

### 3.4 Seguridad

- El acceso directo Supabase con RLS amplia puede eludir la autorización de FastAPI.
- Existe una credencial demostrativa literal versionada que requiere revisión y posible rotación.
- `pip-audit` y el árbol npm de desarrollo informaron dependencias vulnerables.
- Faltan registro estructurado de eventos de seguridad, pruebas con tokens reales y validación del endurecimiento del despliegue.

### 3.5 Accesibilidad y rendimiento

- Formularios reutilizables, modales, mensajes de error y mapas tienen defectos WCAG abiertos.
- No se probó con lector de pantalla ni sobre pantallas autenticadas.
- El bundle principal supera 500 kB minificado.
- No existen mediciones válidas del motor productivo ni de la API con PostgreSQL/PostGIS operativo.

## 4. Causas probables para discutir

Las siguientes son hipótesis derivadas de la evidencia y deben validarse con el equipo:

| Hipótesis | Evidencia asociada | Pregunta para la reunión |
|---|---|---|
| Se desarrollaron Frontend y Backend en paralelo sin un contrato integrado como fuente única. | Doble vía Supabase/FastAPI y DTO distintos. | ¿Cuándo y cómo se acordaron los contratos entre capas? |
| Se priorizó completar pantallas demostrativas antes que persistencia y pruebas E2E. | Funciones visibles con datos/cálculos locales; seis E2E omitidas. | ¿La definición de terminado exigía Backend y persistencia? |
| Los requisitos no funcionales ingresaron tarde al flujo. | SonarQube, seguridad, WCAG y rendimiento se configuraron después del desarrollo principal. | ¿Qué controles deben incorporarse desde el inicio del siguiente Sprint? |
| El entorno de integración no fue definido tempranamente. | Falta PostGIS, tokens/roles, datos controlados y proveedor de tráfico. | ¿Qué entorno mínimo debe estar disponible antes de iniciar una historia? |
| Existen contradicciones documentales sin un mecanismo formal de decisión. | Límites 30/45 s, capacidad, WCAG 2.1/2.2 y alcance de reoptimización. | ¿Quién aprueba y dónde se registra cada decisión? |
| La cobertura y calidad no formaban parte efectiva de la Definition of Done. | Quality Gate en error y cobertura Frontend mínima. | ¿Qué umbrales son obligatorios antes de aceptar una historia? |
| La división de historias pudo ser demasiado horizontal. | UI, Backend y datos existen por separado sin vertical slices completos. | ¿Conviene entregar una historia integrada por vez? |

Estas hipótesis no atribuyen culpa ni describen el desempeño de personas.

## 5. Dificultades de integración observadas

1. Contratos y nombres de campos distintos entre Supabase, modelos React y esquemas FastAPI.
2. Dos fronteras de autorización: RLS Supabase y dependencias de rol FastAPI.
3. Falta de perfiles/tokens aislados para probar administrador, planificador y conductor.
4. Migraciones repartidas entre Supabase y modelos SQLAlchemy sin una secuencia única reproducible.
5. PostGIS ausente en la base aislada.
6. Motor de optimización no seleccionado/implementado y restricciones todavía no aplicadas.
7. Datos geográficos sin geometría vial ni proveedor cartográfico integrado.
8. Contratos ausentes para indicadores, ahorros y comparación de escenarios.
9. Dependencias de desarrollo con alertas que requieren actualización coordinada.
10. Deuda de lint y cobertura que aumenta el costo de modificar componentes existentes.

## 6. Coordinación del equipo

No existe evidencia suficiente para evaluar participación, comunicación, carga de trabajo o desempeño individual. Estos temas deben discutirse con respeto en la reunión.

Puntos sugeridos para validación:

- claridad del objetivo del Sprint y Definition of Done;
- disponibilidad y revisión oportuna de contratos API;
- coordinación entre Frontend, Backend, datos y calidad;
- mecanismo para resolver contradicciones documentales;
- revisión de cambios de seguridad y migraciones;
- disponibilidad de entornos, credenciales y datos de prueba;
- frecuencia de integración y demostraciones parciales;
- propiedad compartida de pruebas y documentación.

## 7. Calidad del código, pruebas y documentación

### 7.1 Calidad del código

Aspectos favorables:

- separación por capas en el Backend;
- cliente HTTP centralizado y validación de entorno;
- contratos Pydantic y errores uniformes;
- controles de autorización Backend;
- corrección verificada de un hallazgo Bandit.

Aspectos a mejorar:

- eliminar la doble arquitectura de acceso a datos;
- reducir 132 code smells reportados por SonarQube;
- resolver deuda ESLint;
- eliminar credenciales demostrativas y endurecer RLS;
- sustituir implementaciones demostrativas por capacidades explícitamente soportadas;
- revisar integridad/unicidad y migraciones.

### 7.2 Pruebas

Aspectos favorables:

- pruebas del Backend pasaron de superficiales a casos de persistencia, contratos, autorización y errores;
- `xfail` y `skip` documentan brechas sin falsear aprobaciones;
- se conservaron reportes JUnit, cobertura y Playwright;
- se reejecutaron pruebas después de una corrección de seguridad.

Aspectos a mejorar:

- elevar cobertura Frontend y del código nuevo;
- añadir pruebas de componentes, store, permisos y servicios Supabase/FastAPI;
- preparar E2E reales por rol;
- ejecutar PostGIS y migraciones en CI;
- incorporar pruebas de contrato entre OpenAPI y tipos Frontend;
- medir optimización, API, accesibilidad y recuperación bajo escenarios reproducibles.

### 7.3 Documentación

Aspectos favorables:

- existen diagnóstico, plan, contratos, casos de prueba, seguridad, SonarQube y accesibilidad/rendimiento;
- las limitaciones y resultados fallidos se conservaron;
- los hallazgos incluyen evidencia y prioridad.

Aspectos a mejorar:

- establecer un único catálogo aprobado de historias y criterios;
- resolver y registrar 30/45 segundos, capacidad objetivo y alcance US-015;
- mantener una matriz requisito–código–prueba–evidencia actualizada;
- versionar documentación solo cuando el equipo lo autorice;
- separar claramente documentación académica, evidencia generada y código fuente.

## 9. Propuesta de experimento para el siguiente Sprint

Seleccionar una sola historia de alto valor —por ejemplo, consulta y actualización de vehículos— y completarla extremo a extremo:

1. aprobar contrato OpenAPI y permisos;
2. preparar migración/datos PostgreSQL;
3. conectar token real;
4. migrar React desde Supabase directo a FastAPI;
5. ejecutar pruebas de contrato, integración, permisos y E2E;
6. medir cobertura, SonarQube, seguridad y accesibilidad;
7. demostrar el flujo y registrar defectos antes de iniciar la siguiente historia.

**Hipótesis del experimento:** entregar una vertical slice completa permitirá detectar antes los conflictos de contrato, autorización, persistencia y entorno.

**Medidas propuestas:** número de defectos detectados antes del punto de control, tiempo de corrección, cobertura del código nuevo, resultado del Quality Gate y cantidad de casos E2E aprobados sin mocks.

La selección de la historia y las métricas definitivas requieren acuerdo del equipo.

## 10. Preguntas para la reunión

1. ¿Qué ayudó realmente a avanzar y debe mantenerse?
2. ¿Qué bloqueó la integración más tiempo y por qué?
3. ¿La Definition of Done exigía una demostración Frontend–Backend persistente?
4. ¿Qué decisión arquitectónica debe resolverse primero?
5. ¿Qué dependencia externa o de entorno debe prepararse antes de comprometer historias?
6. ¿Qué umbrales de pruebas, seguridad, accesibilidad y cobertura son obligatorios?
7. ¿Qué acción puede asumir cada rol sin sobrecargar a una persona?
8. ¿Cómo se verificará que las acciones acordadas se cumplan?

## 11. Cierre provisional

La evidencia muestra progreso técnico en Backend, contratos, automatización y visibilidad de calidad, junto con una brecha importante entre interfaces demostrativas y funcionalidad integrada. El aprendizaje principal propuesto es priorizar historias verticales pequeñas, con entorno y criterios de aceptación disponibles desde el inicio.

Este cierre es **provisional**. Los aspectos positivos percibidos, las causas, las decisiones y los compromisos solo quedarán aprobados después de la reunión de Retrospectiva del Sprint y su registro por el equipo.
