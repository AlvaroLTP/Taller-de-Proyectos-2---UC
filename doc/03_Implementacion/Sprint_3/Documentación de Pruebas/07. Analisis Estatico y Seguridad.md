# 04 Análisis estático y seguridad

## 1. Identificación

- Proyecto: EcoLogística Lima.
- Fase: 6 — Análisis estático y seguridad.
- Rama revisada: `feature/integracion-sprint-3`.
- Fecha de ejecución: 2026-10-27, zona horaria America/Lima.
- Alcance de código: `Programa_Proyectos_2/Backend/app`, `Programa_Proyectos_2/Frontend/src`, pruebas y migraciones Supabase relacionadas.
- Naturaleza de la revisión: análisis local no invasivo. No se atacaron servicios externos ni se modificó la base remota de Supabase.

## 2. Resumen ejecutivo

El análisis identifica tres riesgos abiertos prioritarios:

1. **Crítico — control de acceso eludible:** el Frontend mantiene operaciones CRUD directas contra Supabase. Las políticas RLS finales conceden lectura y escritura total de las tablas operativas a cualquier usuario autenticado, incluido el rol conductor. Esto permite eludir las restricciones de rol y de registro implementadas en FastAPI.
2. **Alto — credencial estática en una migración:** una migración contiene una contraseña demostrativa literal para crear usuarios. El valor no se reproduce en este informe. Al estar versionada, debe considerarse expuesta y requerir eliminación del mecanismo, rotación y revisión del historial bajo autorización.
3. **Alto — cadena de suministro:** `pip-audit` encontró 26 identificadores únicos de vulnerabilidad en cuatro paquetes Python fijados. El árbol npm de producción no reportó vulnerabilidades, pero el árbol completo de desarrollo reportó 27 incidencias, incluidas tres críticas.

No fue posible ejecutar SonarQube porque no existe servidor ni scanner configurado en el entorno y solo se encontró Java 8. Por tanto, **no hay Quality Gate ni métricas Sonar válidas**; “no ejecutado” no significa cero defectos. Se dejó una configuración reproducible y reportes de cobertura compatibles para una futura ejecución autorizada.

## 7. Controles positivos observados

- FastAPI valida algoritmos JWT permitidos, `issuer`, `audience`, expiración y sujeto para tokens asimétricos.
- Los tokens HS256 heredados se verifican contra Supabase Auth en vez de confiar localmente en un secreto compartido.
- Los roles de Backend se resuelven desde `profiles` y se restringen mediante dependencias `PlannerPrincipal` y `AdminPrincipal`.
- La consulta SQL directa observada utiliza parámetros enlazados (`:user_id`).
- CORS usa orígenes configurables y listas explícitas de métodos/cabeceras; la prueba correspondiente aprobó.
- Los manejadores de excepción devuelven errores genéricos y evitan incluir trazas en la respuesta HTTP.
- No se encontraron coincidencias para `dangerouslySetInnerHTML`, `eval`, `new Function`, `os.system`, `shell=True`, `pickle` o `yaml.load` en el alcance revisado.
- `.gitignore` excluye archivos `.env` y conserva únicamente ejemplos sin secretos.

Estos controles reducen riesgo, pero no neutralizan SEC-001 mientras el Frontend pueda omitir la API protegida.

## 8. Corrección aplicada y regresión

Se reemplazó el `assert` de inicialización de la fábrica de sesiones por una excepción explícita en `Backend/app/core/database.py`.

Después de la corrección:

- Bandit: cero hallazgos en 1,436 líneas; ejecución aprobada.
- pytest: 20 aprobadas y 2 `xfail`; sin regresiones nuevas.
- `git diff --check`: sin errores de espacios; solo advertencias de conversión LF/CRLF del entorno Windows.

Incidente de ejecución registrado: una primera repetición de pytest estableció por error `DATABASE_URL` en vez de `TEST_DATABASE_URL`. Esto mezcló la precondición “Backend sin base configurada” de las pruebas de health con la base aislada y produjo 2 fallos, 9 aprobadas y 11 omitidas. No se clasificó como regresión del código. En un proceso limpio, usando únicamente `TEST_DATABASE_URL` para las pruebas de integración, el resultado fue 20 aprobadas y 2 `xfail`.

No se corrigieron SEC-001 a SEC-009 ni SEC-011 a SEC-013 porque requieren decisiones de arquitectura, rotación de cuentas, cambios de esquema o actualizaciones coordinadas con riesgo de compatibilidad.
