# 03.1 Revisión del Sprint

## 1. Identificación

- **Proyecto:** EcoLogística Lima.
- **Sprint evaluado:** Sprint 3.
- **Rama de referencia original:** `avance-sprint-3`.
- **Rama de integración evaluada:** `feature/integracion-sprint-3`.
- **Fecha de revisión técnica:** 27 de octubre de 2026, zona horaria America/Lima.
- **Base de la revisión:** diagnóstico del repositorio, Plan de Trabajo, preparación del Backend, punto de control de integración, pruebas de sistema y E2E, análisis estático y seguridad, SonarQube, accesibilidad y rendimiento.

Estados utilizados:

- **Aprobado:** existe implementación y evidencia reproducible suficiente para el alcance evaluado.
- **Parcialmente cumplido:** existe una parte funcional, pero falta integración, persistencia, cobertura o algún criterio relevante.
- **Pendiente:** la capacidad comprometida no está terminada o depende de una decisión/corrección todavía abierta.
- **No verificable:** no existen entorno, datos, credenciales o evidencia suficientes para confirmar el resultado.

## 2. Objetivo del Sprint

El objetivo técnico reconstruido a partir del código y la documentación consiste en disponer de capacidades de planificación y seguimiento logístico: generar y visualizar rutas, considerar restricciones y congestión, presentar indicadores operativos y estimar ahorros, apoyándose en los datos de pedidos, vehículos y conductores creados en Sprints anteriores.

Para considerar alcanzado ese objetivo, las funciones del Frontend deben consumir contratos reales del Backend, respetar autorización, persistir los resultados y contar con pruebas reproducibles. La existencia de pantallas, la compilación correcta o una simulación local no son evidencia suficiente de integración.

**Estado del objetivo:** **parcialmente cumplido**. Existen interfaces y componentes demostrativos, pero la integración Frontend–FastAPI, el motor de optimización, la persistencia de soluciones, la cartografía real y varios contratos del Sprint 3 permanecen incompletos.

## 6. Resultados de pruebas y calidad

### 6.1 Pruebas funcionales y de sistema

- Resultado consolidado registrado: **20 aprobadas, 2 `xfail`, 0 fallidas**.
- Se aprobaron CRUD Backend, integridad referencial, errores 404/409/422, restricciones por rol a nivel de aplicación, capacidad, CORS, OpenAPI y guardia que evita exponer el optimizador demostrativo como productivo.
- Los dos `xfail` representan brechas reproducibles, no aprobaciones: unicidad vehicular y disponibilidad de PostGIS.

### 6.2 Pruebas E2E

- **2 aprobadas:** presentación/validación del login y mostrar/ocultar contraseña.
- **6 omitidas:** autenticación real y rol, consulta/selección logística, optimización/persistencia, mapa geográfico, indicadores/escenarios y recuperación frente a caída del Backend.
- Las omisiones impiden declarar integración completa.

### 6.3 SonarQube y cobertura

- SonarQube Server 26.10.0.133078 y Scanner 8.1.0.6389 ejecutaron correctamente.
- Resultado: 0 bugs, 0 vulnerabilidades, 0 hotspots, 132 code smells, duplicación 0.4% y cobertura total 9.6%.
- **Quality Gate: `ERROR`** porque la cobertura del código nuevo fue 16.7%, inferior al mínimo configurado de 80%.
- La ejecución correcta de SonarQube no equivale a aprobación del Quality Gate.

### 6.4 Seguridad

- Bandit quedó con 0 hallazgos después de reemplazar un `assert` operativo por una excepción explícita.
- `npm audit --omit=dev` informó 0 vulnerabilidades de producción; el árbol completo informó 27 incidencias en herramientas/desarrollo.
- `pip-audit` informó 26 identificadores únicos en cuatro paquetes fijados.
- Persisten riesgos críticos/altos de control de acceso, credencial demostrativa versionada, cadena de suministro y persistencia/integridad.

### 6.5 Accesibilidad y rendimiento

- Lighthouse login: rendimiento 99 móvil/100 escritorio; accesibilidad 94 en ambos perfiles.
- Defecto automático: objetivo táctil de mostrar contraseña de 18 × 18 px.
- Defectos manuales: asociación de etiquetas, semántica/foco de modales, anuncio de errores y alternativa del mapa.
- Bundle principal: 613.78 kB minificado y 159.96 kB comprimido.
- No existe una medición válida de la API con PostgreSQL/PostGIS operativo ni del algoritmo productivo.

## 8. Limitaciones técnicas y decisiones pendientes

1. Resolver el límite de optimización aplicable: 30 o 45 segundos.
2. Aprobar la capacidad objetivo de pedidos y vehículos.
3. Confirmar si US-015/reoptimización pertenece al Sprint 3 o Sprint 4.
4. Aprobar la frontera de seguridad: FastAPI como única vía de datos o políticas RLS equivalentes por rol/propiedad.
5. Definir el motor de optimización, el proveedor de tráfico y la fuente cartográfica.
6. Definir línea base y fórmulas para indicadores y ahorros.
7. Preparar usuarios, perfiles y tokens aislados para los roles administrador, planificador y conductor.
8. Preparar PostgreSQL/PostGIS reproducible con migraciones y datos de prueba.
9. Confirmar WCAG 2.2 AA como línea base del proyecto frente a documentación previa que menciona WCAG 2.1.

No se adopta ninguna de estas decisiones de forma unilateral en esta revisión.

### Decisión técnica de revisión

**Sprint 3: parcialmente cumplido y no apto todavía para declararse terminado o listo para producción.**
