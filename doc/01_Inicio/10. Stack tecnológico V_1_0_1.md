# 10. Stack tecnológico V_1_0_1

## 1. Propósito del Documento
Definir y justificar la selección de tecnologías que soportarán la plataforma web EcoLogística Lima, considerando los requisitos funcionales, no funcionales, las restricciones presupuestarias, los objetivos de sostenibilidad y las necesidades de procesamiento del problema de optimización de rutas Green VRPTW.

La selección tecnológica constituye una decisión de arquitectura que deberá validarse mediante pruebas de integración, rendimiento, mantenibilidad y consumo de recursos.

## 2. Evaluación Multidimensional de Alternativas
Para asegurar una decisión objetiva, se evaluaron tres (3) alternativas arquitectónicas dominantes en la industria, tomando como base las directrices de eficiencia, escalabilidad y la experiencia previa del equipo. Se añadió un quinto criterio fundamental para nuestro caso de negocio: la capacidad para procesar modelos matemáticos complejos (Metaheurísticas).

| Criterio de Evaluación | Alternativa 1: MERN (Node/Express + React + MongoDB) | Alternativa 2: Python / FastAPI + React + PostgreSQL | Alternativa 3: Java Spring Boot + Angular + PostgreSQL |
| :--- | :--- | :--- | :--- |
| **Curva de Aprendizaje** | Baja (JavaScript unificado) | Media (Python backend, JS frontend) | Alta (Verboso, Fuertemente tipado) |
| **Costo de Infraestructura** | Moderado (Node async I/O) | Bajo (FastAPI asíncrono, bajo consumo RAM) | Alto (Mayor consumo de memoria JVM) |
| **Soporte Comunitario** | Masivo / Muy Alto | Alto / Crecimiento acelerado | Masivo / Corporativo consolidado |
| **Eficiencia Energética / Eco-Design** | Media | Alta (Métricas de cómputo eficientes) | Media-Baja (Warm-up JVM prolongado) |
| **Idoneidad para Metaheurísticas (Green VRPTW)* (Criterio añadido)** | Baja (Ecosistema matemático/científico limitado) | Muy Alta (Ecosistema científico robusto, librerías como DEAP, OR-Tools nativas) | Media (Librerías maduras, pero mayor tiempo de desarrollo) |

## 3. Justificación Técnica Formal de la Selección
Tras el análisis riguroso de la matriz comparativa, la Dirección del Proyecto determina que la **Alternativa 2 (Python / FastAPI + React + PostgreSQL)** es la única combinación que satisface integralmente las restricciones operativas, económicas y de cronograma del proyecto "EcoLogística Lima". La justificación formal se desglosa en los siguientes ejes:

* **Priorización y Motor del Aplicativo Web (React):**
  Se determina el uso de **React** como la tecnología núcleo para la capa de presentación (Frontend). Si bien Angular (Alt 3) ofrece un marco corporativo sólido, su curva de aprendizaje alta representa un riesgo inaceptable para nuestro ciclo de desarrollo híbrido de 12 semanas. En una comparación justa, React supera a las alternativas por tres factores críticos: 
  1) El **perfil y experiencia demostrada del equipo de desarrollo** en este modelo de programación reduce drásticamente los tiempos de iteración. 
  2) El uso del *Virtual DOM* de React garantiza un renderizado de altísimo rendimiento, vital para la actualización fluida del mapa interactivo (Leaflet/OpenStreetMap) y del dashboard en tiempo real en dispositivos con conectividad intermitente en zonas como San Juan de Lurigancho.
  3) Su ecosistema masivo de componentes facilita el cumplimiento estricto del estándar de accesibilidad **WCAG 2.1 nivel AA** exigido para nuestros conductores.

* **Capacidad de Procesamiento y Metaheurísticas (Python/FastAPI):**
  Python constituye una alternativa adecuada para desarrollar el motor de optimización por la disponibilidad de bibliotecas de investigación operativa y optimización combinatoria, como OR-Tools, así como herramientas para implementar y evaluar metaheurísticas.

FastAPI permitirá exponer las funcionalidades del backend mediante interfaces API y facilitar la integración con el frontend.

La capacidad de generar rutas en un máximo de 45 segundos para escenarios de hasta 150 pedidos y 15 vehículos constituye un objetivo de rendimiento que deberá verificarse mediante pruebas con datos representativos. La selección de Python y FastAPI no garantiza por sí sola el cumplimiento de dicho umbral.

* **Persistencia de Datos y Escalabilidad (PostgreSQL):**
  Frente al enfoque NoSQL de MongoDB (Alt 1), PostgreSQL asegura la integridad relacional estricta requerida para gestionar flotas, conductores y entregas. Adicionalmente, su extensión espacial (PostGIS) nos brinda escalabilidad futura (hasta 1,000 pedidos/día) y procesamiento nativo de geolocalización.

* **Bajo Consumo Energético en la Nube (Green Software / Eco-Design):**
  La arquitectura seleccionada favorecerá la utilización eficiente de recursos computacionales mediante dimensionamiento adecuado de infraestructura, monitoreo del consumo, optimización de consultas y reducción de procesamiento innecesario.

El uso de Python, FastAPI y PostgreSQL no demuestra automáticamente una menor huella ambiental frente a otras tecnologías. Cualquier afirmación sobre eficiencia energética deberá sustentarse mediante métricas comparables de consumo de recursos y carga de trabajo.

El despliegue deberá considerar el presupuesto monetario directo máximo de S/ 500 establecido en el Acta de Constitución y los principios de sostenibilidad pertinentes al proyecto.
