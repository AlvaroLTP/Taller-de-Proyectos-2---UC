## 1. Propósito

Este documento analiza las restricciones del proyecto **EcoLogística Lima** desde cuatro dimensiones exigidas: **Salud y Seguridad Pública**, **Análisis de Costo del Ciclo de Vida (LCC)**, **Cero Carbono Neto y Sostenibilidad**, y **Aspectos Culturales, Sociales y Económicos**.

El objetivo es convertir cada restricción en decisiones de diseño, controles verificables y evidencias de cumplimiento, evitando que el análisis quede únicamente en declaraciones generales.

---

## 2. Línea base documental utilizada

Para evitar introducir valores contradictorios, este documento adopta como línea base de gobierno el **Acta de Constitución V_1_0_0**, que establece para el PMV:

- duración planificada de **12 semanas**;
- gasto monetario directo máximo de **S/ 500**;
- arquitectura web con separación frontend/backend;
- objetivo de rendimiento del optimizador de **≤ 30 s para hasta 50 puntos y 5 vehículos** en el escenario de referencia;
- uso de software open source, free tiers y consumo controlado de APIs;
- aplicación de controles de privacidad si se tratan datos personales;
- carácter de **apoyo a la decisión**, no de conducción o despacho autónomo de misión crítica.

El análisis LCC a tres años exigido en esta actividad se utiliza como **horizonte de evaluación de sostenibilidad económica de la solución**, no como autorización de un presupuesto productivo de tres años que no ha sido aprobado en el Acta.

# 4. Análisis por dimensión

## 4.1. Salud y Seguridad Pública

### 4.1.1. Riesgos

1. **Privacidad:** exposición de direcciones, teléfonos, identificadores y ubicaciones.
2. **Acceso indebido:** un usuario consulta o modifica información fuera de su rol.
3. **Credenciales/secretos:** filtración de contraseñas o claves de APIs en repositorio o logs.
4. **Integridad de datos:** coordenadas, capacidades o ventanas horarias incorrectas generan rutas inválidas.
5. **Seguridad operativa:** una recomendación no actualizada respecto de restricciones viales, incidentes o condiciones locales puede inducir una decisión inadecuada.
6. **Exceso de confianza:** presentar una estimación del algoritmo como instrucción autónoma o garantía de seguridad.

### 4.1.2. Controles de diseño

| Control | Implementación esperada | Evidencia |
|---|---|---|
| SSP-C01 — Minimización | Persistir solo datos necesarios para los casos de uso del PMV. | Modelo de datos y revisión de campos. |
| SSP-C02 — Autorización | RBAC con principio de mínimo privilegio. | Matriz de roles + pruebas 403/denegación. |
| SSP-C03 — Contraseñas | Hash mediante Argon2id, bcrypt o algoritmo equivalente adecuado; nunca texto plano. | Configuración y prueba de registro/login. |
| SSP-C04 — Transporte | HTTPS; preferencia por TLS 1.3 y mínimo TLS 1.2 según soporte del proveedor. | Inspección del endpoint desplegado. |
| SSP-C05 — Reposo | Base de datos y backups cifrados por el servicio cloud; objetivo AES-256 o mecanismo equivalente del proveedor. | Configuración del servicio / documentación del proveedor. |
| SSP-C06 — Secretos | Variables de entorno o secret manager; `.env` excluido mediante `.gitignore`. | Revisión de repositorio. |
| SSP-C07 — Logs | No registrar tokens, contraseñas, claves de API ni datos personales innecesarios; pseudonimizar identificadores cuando sea suficiente. | Muestra de logs y checklist. |
| SSP-C08 — Validación | Validar rangos, coordenadas, capacidad, ventanas y restricciones antes de optimizar. | Casos de prueba de entradas inválidas. |
| SSP-C09 — Revisión humana | La UI identifica la ruta como recomendación y permite rechazar/recalcular. | Prueba funcional / criterio de aceptación. |
| SSP-C10 — Retención | Definir tiempo de retención para datos y logs de prueba; eliminar datasets personales cuando dejen de ser necesarios. | Política breve de retención. |

### 4.1.3. Cumplimiento normativo relacionado

- **Ley N.º 29733, Ley de Protección de Datos Personales (Perú).**
- **Decreto Supremo N.º 016-2024-JUS**, Reglamento vigente de la Ley N.º 29733.
- **OWASP Top 10**, como referencia para riesgos de aplicación web.
- **TUO del Reglamento Nacional de Tránsito — D.S. N.º 016-2009-MTC y modificatorias**, como referencia normativa vial cuando corresponda al modelado de restricciones.

El PMV no debe afirmar certificación legal ni de ciberseguridad; debe demostrar controles de diseño y pruebas acordes con su alcance.

## 4.2. Análisis de Costo del Ciclo de Vida (LCC)

### 4.2.1. Restricción económica

La línea base vigente establece un máximo de **S/ 500 de gasto monetario directo para el PMV**. Por ello, la solución debe demostrar no solo bajo costo de construcción académica, sino también **evitar decisiones que generen lock-in o costos recurrentes difíciles de sostener**.

### 4.2.2. Modelo de cálculo

Para evaluar la sostenibilidad económica a tres años se propone:

**LCC(3 años) = Costo inicial del PMV + Σ Costos operativos anuales + Costos de cambio/migración − Créditos/beneficios aplicables**

Los costos operativos deben considerar, como mínimo:

- hosting del frontend;
- ejecución del backend;
- base de datos y almacenamiento;
- mapas, geocodificación, matrices y tráfico;
- dominio/certificados si generan costo;
- backups y observabilidad;
- transferencia de datos;
- mantenimiento correctivo/evolutivo cuando sea valorizado;
- costo eventual de migración de proveedor.

Las horas académicas del equipo no se incorporan al límite monetario de S/ 500 mientras el Acta mantenga esa definición, pero pueden valorizase por separado para un estudio económico ampliado.

### 4.2.3. Estrategias LCC

1. **Open source por defecto:** React, Python/FastAPI, PostgreSQL/PostGIS, Leaflet y OpenStreetMap cuando sus políticas de uso lo permitan.
2. **Escalado según demanda:** preferir servicios que permitan apagar, suspender o reducir recursos cuando no hay uso.
3. **Una arquitectura simple:** evitar microservicios, Kubernetes, colas y caches distribuidos si no existe evidencia de necesidad.
4. **Control de APIs:** límites diarios/mensuales, alertas de cuota y manejo de error antes de incurrir en sobreconsumo.
5. **Abstracción de proveedor:** los servicios geoespaciales deben consumirse mediante adaptadores reemplazables.
6. **Eficiencia de consultas:** índices B-tree/GiST, consultas parametrizadas y eliminación de N+1.
7. **Backups proporcionales:** frecuencia y retención acordes con el valor y volumen de los datos del PMV.

### 4.2.4. Escenarios LCC

| Escenario | Supuesto | Decisión |
|---|---|---|
| **Base académico** | Uso esporádico, datasets de prueba, free tiers/créditos. | Mantener el gasto total del PMV dentro de la línea base S/ 500. |
| **Piloto limitado** | Uso periódico por un grupo pequeño, más consultas geoespaciales. | Medir costo mensual real antes de ampliar capacidad. |
| **Crecimiento** | Mayor volumen, más disponibilidad y almacenamiento. | Reestimar TCO, comparar proveedores y aprobar nueva línea base antes de producción. |

No se fija un monto de operación a tres años porque actualmente no existe una línea base aprobada para dicho horizonte.

## 4.3. Cero Carbono Neto y Sostenibilidad

### 4.3.1. Principio de integridad ambiental

EcoLogística Lima busca **reducir y comparar impactos**, pero un PMV no debe equiparar automáticamente “menor distancia” con “cero carbono neto”. La neutralidad climática exige un alcance de emisiones, método de cuantificación y tratamiento de emisiones residuales que superan el alcance de una simple optimización de rutas.

### 4.3.2. Restricciones de diseño sostenible

| Control | Aplicación |
|---|---|
| CNZ-C01 — Cómputo eficiente | Establecer límites de iteraciones/tiempo del optimizador y medir duración por escenario. |
| CNZ-C02 — Base de datos eficiente | Índices, consultas espaciales selectivas y reducción de transferencia innecesaria. |
| CNZ-C03 — Infraestructura adecuada | Evitar recursos sobredimensionados y servicios permanentemente activos sin carga. |
| CNZ-C04 — APIs externas | Reducir solicitudes redundantes y reutilizar resultados dentro de su vigencia/licencia. |
| CNZ-C05 — Métricas logísticas | Documentar factores de consumo/emisión, unidad, fuente y supuestos. |
| CNZ-C06 — Transparencia | Mostrar “emisiones estimadas” y no “emisiones reales” cuando no exista medición directa. |
| CNZ-C07 — Proveedor cloud | Considerar reportes públicos de energía renovable, intensidad de carbono y región de despliegue como criterio secundario de selección. |
| CNZ-C08 — Comparación | Evaluar escenario base vs. optimizado con distancia, tiempo, combustible/energía y CO₂e estimado. |

### 4.3.3. Referencia metodológica

**ISO 14083:2023** establece una metodología común para cuantificar y reportar emisiones de gases de efecto invernadero de operaciones de cadenas de transporte. Para el PMV se utiliza como referencia metodológica y no como certificación.

### 4.3.4. Indicadores recomendados

- km totales por escenario;
- tiempo total planificado;
- combustible o energía estimada;
- kg CO₂e estimados por escenario;
- kg CO₂e por entrega;
- porcentaje de reducción frente al baseline;
- tiempo de cómputo del optimizador;
- cantidad de llamadas a servicios externos por optimización.

## 4.4. Aspectos Culturales, Sociales y Económicos

### 4.4.1. Restricciones glocales

El sistema se diseña para Lima Metropolitana, donde pueden coexistir:

- direcciones con nomenclatura incompleta o referencias por manzana/lote;
- puntos de referencia informales;
- conectividad móvil variable;
- dispositivos de gama media/baja;
- diferentes niveles de alfabetización digital;
- horarios variables de comercios;
- vías pavimentadas y no pavimentadas;
- información de tráfico incompleta o cambiante.

### 4.4.2. Estrategias de inclusión y accesibilidad

1. **WCAG 2.1 nivel AA** como baseline de accesibilidad.
2. Contraste y navegación por teclado en las funciones principales.
3. Etiquetas y mensajes de error comprensibles.
4. Controles táctiles suficientemente grandes en vistas utilizadas desde móvil.
5. Evitar que el significado dependa únicamente del color; los niveles de congestión deben acompañarse con texto/icono.
6. Layout responsive y reducción de recursos pesados.
7. Carga diferida de elementos no críticos del mapa/dashboard.
8. Formularios capaces de registrar dirección textual, coordenadas y puntos de referencia.
9. Lenguaje operativo en español y terminología comprensible para usuarios locales.
10. Arquitectura de textos externalizables para permitir i18n futura sin convertirla en requisito obligatorio del PMV.
11. Modo simplificado para conductor: ruta asignada, entregas pendientes y alertas relevantes.
12. Mensajes explícitos cuando datos externos —por ejemplo tráfico— no estén disponibles.

### 4.4.3. Restricción económica del usuario

La solución no debe exigir hardware especializado ni una aplicación móvil nativa. La experiencia principal debe poder operar en un navegador moderno y adaptarse a pantallas pequeñas, reduciendo barreras de adopción.

# 6. Priorización de restricciones

| Prioridad | Restricción | Justificación |
|---|---|---|
| **Crítica** | Privacidad y control de acceso | Impacta datos personales y confianza del sistema. |
| **Crítica** | Integridad de datos de entrada y ruta | Datos incorrectos pueden invalidar la optimización y afectar decisiones operativas. |
| **Crítica** | Presupuesto máximo del PMV | Es una línea base formal del proyecto. |
| **Alta** | Dependencia/costo de APIs | Puede bloquear geocodificación, matriz de tiempos o mapas. |
| **Alta** | Accesibilidad y baja conectividad | Afecta adopción y uso por perfiles operativos. |
| **Alta** | Transparencia ambiental | Evita afirmaciones de sostenibilidad no sustentadas. |
| **Media** | Preparación para i18n | Conveniente para evolución, no esencial para el PMV local. |
| **Media** | Selección de región/proveedor cloud por intensidad de carbono | Importante, pero subordinada a disponibilidad, costo y viabilidad académica. |

# 9. Criterio de aceptación del documento

El documento se considera aceptado cuando:

1. las cuatro dimensiones exigidas están analizadas;
2. cada dimensión contiene una restricción explícita y una estrategia de mitigación/diseño;
3. los controles críticos cuentan con una evidencia verificable;
4. no se contradice la línea base de alcance, tiempo y costo del Acta;
5. las referencias normativas aplicables están identificadas;
6. las restricciones se reflejan en arquitectura, backlog y pruebas del PMV.
